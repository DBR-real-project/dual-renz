# 시연 가이드 — 심사장에서 이대로만 하면 된다

작성: 2026-08-09 | 대상: 발표자·시연 담당

목표는 **세 등급(초록/노랑/빨강)을 모두 보여주고, 두 엔진이 독립적으로 동작한다는 것**을
증명하는 것이다. 아래 순서대로 하면 3~4분에 끝난다.

---

## 0. 시연 30분 전 점검 (반드시)

```powershell
cd C:\Users\migle\DualGuard-MediaAnalysis

# ① 시연 파일 세 개가 다 있는지
dir data\korean_calls\scam_call.wav          # 빨강용
dir data\korean_calls\normal_call.wav        # 노랑용
dir data\korean_calls\real_normal_call.wav   # 초록용 — 없으면 아래 한 줄로 생성
.venv\Scripts\python.exe scripts\fetch_korean_speech_samples.py

# ② 엔진이 전부 준비됐는지 — 모델을 미리 로드해 첫 분석 지연을 없앤다
.venv\Scripts\python.exe scripts\analyze_call.py --input data\korean_calls\scam_call.wav --quiet

# ③ 서버 기동
.venv\Scripts\python.exe scripts\run_server.py
#    → http://127.0.0.1:8000 접속해서 상단 칩이 초록인지 확인
```

**메모리 확인.** 브라우저 탭을 많이 열어두지 말 것. 여유 6GB 아래로 떨어지면
분석 도중 프로세스가 죽는다(원인과 대응은 `blocked_and_next.md` 3-3).
작업관리자에서 사용 가능 메모리를 한 번 보고 시작하는 게 안전하다.

**첫 분석은 느리다.** 모델을 처음 로드하는 데 시간이 걸리므로, ①을 미리 돌려두면
시연 중에는 빠르게 나온다. 이 단계를 건너뛰지 말 것.

## 1. 빨강 — 사기 통화 (핵심 시연)

`data\korean_calls\scam_call.wav` 업로드

**기대 결과**
- Fraud Risk Score **100 / 높음** — "즉시 통화를 종료하세요"
- 8개 구간이 전부 빨강, 구간별로 다른 기법이 잡힘
- 각 구간에 유사 사기 사례가 붙음

**말할 것**
> "78초 통화를 8개 발화 구간으로 나눠 분석했습니다. 구간마다 어떤 사회공학
> 기법이 쓰였는지, 그리고 실제 어떤 수법 사례와 유사한지를 근거로 제시합니다.
> 점수만 보여주는 게 아니라 **왜 위험한지**를 보여주는 게 핵심입니다."

**구간 하나를 클릭해서** 근거(걸린 표현 + 유사 사례)를 펼쳐 보이면 효과가 크다.

## 2. 초록 — 정상 통화 (진짜 사람 목소리)

`data\korean_calls\real_normal_call.wav` 업로드

파일이 없으면 한 번만 만들면 된다 (사람이 녹음할 필요 없다):

```powershell
.venv\Scripts\python.exe scripts\fetch_korean_speech_samples.py --verify
```

공개 한국어 음성 코퍼스 **Zeroth-Korean**(CC BY 4.0)에서 실제 사람이 녹음한
발화를 가져와 40초짜리 정상 통화를 만든다. 매번 같은 파일이 나온다.

**기대 결과** (실측, 재현됨)
- Fraud Risk Score **9.3 / 낮음** — "특별한 위험 신호가 없습니다"
- 콘텐츠 위험도 **0.0** — 걸린 기법 없음
- 미디어 위험도 **26.7** — 진짜 목소리로 판정

**말할 것**
> "같은 파이프라인에 정상 통화를 넣으면 초록이 나옵니다. **헛경보를 내지 않는다는
> 게 이 시스템에서 가장 중요합니다.** 사기라고 잘못 알리는 순간 아무도 안 씁니다."

> ⚠ 저장소의 `normal_call.wav`(Windows TTS)로는 초록이 안 나온다. 음성 자체가
> 합성이라 AASIST가 정확히 잡아 미디어 100 → 중간이 된다. 그건 3번에서 쓴다.

본인 목소리로 직접 녹음하고 싶으면 `record_call_sample.py`도 그대로 쓸 수 있다.

## 3. 노랑 — 내용은 정상인데 목소리가 합성 (교차검증 ①)

`data\korean_calls\normal_call.wav` 업로드 (저장소에 이미 있는 TTS 파일)

**기대 결과**: 콘텐츠 위험도 **0** / 미디어 위험도 **100** → **35.0 중간(노랑)**

**말할 것**
> "대화 내용은 완전히 정상입니다. 그런데 목소리가 합성이라 경고가 뜹니다.
> 화법만 보는 솔루션은 이걸 못 잡습니다."

반대 방향(**목소리는 진짜인데 화법이 사기**)까지 보여주려면 사람이 사기 대본을
읽어 녹음해야 한다 — `record_call_sample.py --script scam`. 시간이 없으면
아래 4조합 표로 대신해도 된다:

```powershell
.venv\Scripts\python.exe scripts\demo_cross_validation.py
```

| 클립 | 영상 | 음성 | media_risk | 정상 대화와 함께면 |
|---|---|---|---|---|
| 진짜+진짜 | 18.8 | 3.7 | 18.8 | 6.6 낮음 🟢 |
| 딥페이크+진짜 | **100.0** | 3.7 | 100.0 | 35.0 중간 🟡 |
| 진짜+합성 | 18.8 | **100.0** | 100.0 | 35.0 중간 🟡 |
| 딥페이크+합성 | **100.0** | **100.0** | 100.0 | 35.0 중간 🟡 |

오른쪽 열이 핵심이다 — **어느 채널이든 하나만 위조돼도 경고가 뜬다.**

## 3-1. 마무리 한 컷 — 분석 히스토리

앞의 세 건을 순서대로 돌렸다면, 결과 화면 아래 **분석 히스토리** 카드에
빨강·노랑·초록이 그대로 쌓여 있다. 추이 그래프 한 장이 "세 등급이 다 나온다"는
증거가 되므로 **마지막에 스크롤해서 한 번 보여주고 끝내는 것을 권한다.**

**말할 것**
> "분석 결과는 저장돼서 나중에 다시 볼 수 있고, 위험도 추이도 남습니다.
> 다만 **통화 파일 원본은 분석 직후 서버에서 지웁니다.** 남는 건 결과뿐입니다.
> 개인정보를 다루는 서비스라 처음부터 그렇게 설계했습니다."

시연 순서를 1→2→3으로 지키면 별도 준비가 필요 없다. 순서를 바꿔 돌렸거나
서버를 새로 띄웠다면 히스토리가 비어 보일 수 있으니, 0번 사전 점검 때
한 번씩 미리 올려두면 안전하다 (기록은 서버를 재시작해도 남는다).

## 4. 예상 질문과 답변

**"정확도가 얼마나 되나요?"**
> 세 엔진을 각각 실측했습니다. 음성 스푸핑은 정탐 96.7% / 오탐 0%,
> 영상 딥페이크는 정탐 73.3% / 오탐 0%, 콘텐츠 화법 분류는 정확도 90.5%입니다.
> 영상 수치는 **5-겹 교차검증** 값입니다 — 점수 보정 파라미터를 맞춘 데이터로
> 그대로 평가하면 부풀려지기 때문에 따로 냈습니다.
> 다만 **검증 조건을 함께 말씀드려야 합니다.** 음성·영상은 각 모델의 학습
> 도메인 안에서 측정한 값이고, 콘텐츠는 팀이 직접 만든 21건 시나리오입니다.
> 공개 벤치마크 점수가 아닙니다.

**"영상 정탐률 73.3%면 낮은 것 아닌가요?"** ← 먼저 밝히는 게 낫다
> 모델이 학습한 3개 조작 기법(Deepfakes/Face2Face/FaceSwap)은 **5/5 전부, 평균
> 100점**으로 잡습니다. 놓치는 건 2020년 이후 추가된 FaceShifter 같은 미학습
> 기법입니다. 이건 저희 구현 문제가 아니라 딥페이크 탐지 분야의 일반화 한계이고,
> 오탐률이 0%라는 점이 더 중요합니다. 헛경보를 내지 않습니다.

**"LLM 없이도 되나요?"**
> 네. 지금 이 시연도 API 키 없이 돌아가고 있습니다. 한국어 임베딩 기반 오프라인
> 분류기가 정확도 90.5%를 냅니다. LLM을 붙이면 더 올라갈 여지가 있습니다.

**"실시간으로 되나요?"**
> 됩니다. 세션 API로 모델을 상주시키고 5초 청크를 누적 분석합니다.
> 실측으로 **오디오 78초를 26초에 처리**했습니다 — 약 3배속이라 실시간을 따라갑니다.
> 다만 실시간 경로는 **음성과 화법만** 봅니다. 영상 딥페이크는 프레임마다 얼굴 검출과
> Xception 추론이 필요해 실시간 예산에 안 맞아서, 통화가 끝난 뒤 파일 분석에서 봅니다.
> 본선 범위는 기획서대로 업로드 기반이고, 실시간은 Phase 2로 미리 구현해 둔 것입니다.

**"시연에 쓴 통화는 실제 녹취인가요?"** ← 물어보면 숨기지 말 것
> 아닙니다. 세 개 다 시연용으로 만든 파일입니다. 빨강·노랑은 저희가 쓴 대본을
> TTS로 읽힌 것이고, 초록은 공개 한국어 음성 코퍼스 Zeroth-Korean(CC BY 4.0)에서
> **실제 사람이 녹음한 발화**를 가져와 이어 붙인 것입니다. 실제 피해 녹취는
> 개인정보라 쓸 수 없어서, 진짜 사람 목소리가 필요한 초록만 공개 코퍼스로 대체했습니다.

**"오탐이 나면 어떻게 하나요?"**
> 설계 원칙으로 **확정 판정을 하지 않습니다.** "위험 가능성 약 OO%"로 표시하고,
> 왜 그렇게 판단했는지 근거 문장과 유사 사례를 항상 함께 보여줍니다.
> 사용자가 스스로 판단할 수 있게 하는 것이 목표입니다.

## 5. 하지 말아야 할 것

- **서버와 CLI를 동시에 돌리지 말 것** — 메모리 부족으로 죽는다.
- **처음 보는 파일을 즉석에서 올리지 말 것** — 얼굴이 안 잡히거나 무음이면
  결과가 비게 된다. 미리 돌려본 파일만 쓴다.
- **수치를 조건 없이 인용하지 말 것** — "정확도 90%"만 말하면 질문에서 무너진다.
  검증 조건을 먼저 밝히면 오히려 신뢰를 얻는다.
- **크롬 확장은 미리 브라우저에 올려보지 않았다면 시연하지 말 것** — 자동 검증
  (`node scripts/test_extension.js`)은 통과했지만 **권한 승인과 실제 탭 캡처는
  브라우저에서만 확인된다.** 심사장에서 처음 눌러 보지 말 것(`blocked_and_next.md` 1-2).
- **`real_normal_call.wav`를 "실제 통화 녹취"라고 소개하지 말 것** — 공개 코퍼스의
  낭독 음성을 이어 붙인 것이다. 진짜 사람 목소리인 건 맞지만 통화는 아니다.
  출처는 `data\korean_calls\real_normal_call_출처.txt` 에 남겨뒀다.

## 6. 문제가 생겼을 때

| 증상 | 대응 |
|---|---|
| 분석 중 프로세스가 조용히 죽음 | 메모리 부족. 브라우저 탭 정리 후 서버 재시작 |
| 첫 분석이 아주 느림 | 모델 최초 로드. 0번 사전 점검을 안 한 것 |
| 대시보드 상단 칩이 회색 | 해당 엔진 미준비. `/api/health`로 확인 |
| 얼굴 검출 0% 경고 | 정면 얼굴이 없는 영상. 다른 샘플로 교체 |
| 업로드가 거부됨 | 지원 형식 확인 (wav mp3 m4a flac mp4 mov webm, 200MB 이하) |
